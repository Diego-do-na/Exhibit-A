# How this was built

This is a factual account of the repository history and shared task log, not a marketing claim. The repository guide describes a Cauce-coordinated, multi-agent workflow: tasks were assigned from a board, worked in task branches, and integrated through merge commits. The log is the source for the attribution table below.

## The idea in one paragraph

Exhibit A was built around a narrow claim: a security suspicion becomes a finding only when an exploit fails on the vulnerable code for the intended oracle-observed effect in an isolated and resource-limited sandbox, then passes after a fix while baseline and bypass checks remain valid. The CLI, ledger, live view, benchmark harness, and model roles are surfaces around that proof loop. A green result means “nothing could be proven”, never “safe”.

## Spec first

`SPEC.md` is the authoritative product contract: it defines the proof standard, loop, schemas, effects, sandbox and oracle boundaries, security model, scope tiers, and non-goals. `AGENTS.md` turns that contract into the working rules every agent was instructed to read: stay in scope, treat model output and diffs as untrusted, use isolated and resource-limited execution, keep tests honest, and report what was not verified. The shared log records each completed task and its pending work.

## Workflow

The repository guide records a task-board workflow coordinated by Cauce, with 54 board tasks, task branches named `task/Txxx`, declared scope/dependencies/tests, and `merge: Txxx` commits. The task instructions also required one branch and worktree per task, tests declared per task, owner-run full-suite checkpoints, and merge only on green. Agents were not treated as unsupervised authorities: the owner supervised the work, reviewed reports and changes, and performed checkpoint validation and merges.

This repository does not support reducing the attribution record to exactly five identities: `docs/common.md` contains 114 task-log lines and 12 exact labels, because it includes cloud/model variants, corrections, and one human note. ## Guardrails

- The sandbox is isolated and resource-limited; the repository explicitly avoids claiming it is “100% safe”.
- The oracle was red-teamed against false proofs and recall gaps; residual limits are recorded as strict xfails rather than hidden.
- Strict xfails document declared oracle limits; tests were not weakened, deleted, skipped, or converted to non-strict xfails to make results look green.
- Model output and PR/diff content are untrusted data: schemas validate them, and untrusted code is not executed outside the sandbox.
- The proof loop requires baseline, intended oracle effect, provenance, repeatability, and verified fixing/defender checks before `proven`. A green result means “nothing could be proven”, never “safe”.
